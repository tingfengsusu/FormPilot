# 重构设计：把「填表」抽成引擎，与业务、基建分离

> 一句话目标：**引擎只懂"怎么操作页面"，不懂任何业务；基建不懂业务也不懂页面；业务层自己知道要什么。**
>
> 起因：学平险是第一个（也是唯一的）场景，页面知识、业务规则、浏览器动作天然混在一起。
> 现在要接第二条、第三条业务（安全评价、培训报名），必须先把边界划出来，
> 否则每来一个新场景都要改引擎代码 —— 那就等于没有模块。

---

## 零、结论先行

**「填表」确实已经是一个可复用模块，而且已经复用过一次**——仓库里有一份非保险场景的品种配置
（`config/product_library/在线验证_12306余票查询.yaml`，填真实的 12306 表单，含 `fill_mode: autocomplete`
联想框策略）和对应测试（`tests/test_online_12306.py`，离线自动跳过）。
这说明"品种（Product）+ 定位/填写/回读"这套抽象从来不是保险专用的。

**但现在的边界是漏的**：引擎里有保险字段词汇、基建里有业务名词、业务模块里内联着浏览器动作（共 10 处，见第三节）。
所以这次拆分要做的不是"创造一个引擎"，而是**把已存在的引擎擦干净、把业务知识移出去、再加一道守卫防止反向依赖**。

---

## 一、可复用的边界：哪一半能复用

| ✅ 复用度高（机制，进引擎） | ❌ 复用度低（数据/业务，出引擎） |
|---|---|
| 稳定 locator 的探测与优先级（`#id` → `[placeholder]` → `[aria-label]` → 稳定 class → 路径） | 具体页面的 locator 本身 |
| 定位歧义的候选打分、`>> nth=N` 的稳定性处理 | 场景的字段清单（学校/年级/班级 vs 别的东西） |
| 下拉面板作用域内的选项抓取（防止抓到别的下拉的选项） | 选项集与别名表（探针采到的权威数据） |
| 遮挡弹窗的检测与点击把关（投保须知每次点击都重现那类） | 级联关系（学生类别 → 年级/班级） |
| 日期选择器的闭环修正（点 → 读回 → 按列修正） | 期限规则（起期下界、止期 = 起期 + 364） |
| 回读校验（`verifier`）：填完必读回、不猜 | 业务校验（年龄范围、资格要求） |
| 数据源插件协议（Excel / 证件 OCR / 户口本 OCR / 消息 / 人工） | 落库目标与提交策略（是否允许自动提交、人工卡点在哪） |
| 探针流程本身（把权威选项落成配置文件） | 台账结构、状态机、复核规则 |

> **判据一句话**：复用度高的是"怎么操作页面"，复用度低的是"这个页面长什么样、这条业务要什么"。
> 推论：**引擎代码里不允许出现任何具体字段名或业务词** —— 出现了就说明没抽干净。

## 二、现状：三层已经长出来，边界是漏的

### 2.1 三层现状（按依赖方向判断归属，不按目录）

| 层 | 现在在哪 | 行数 | 判断 |
|---|---|---|---|
| **基建** | `gateway/` `orchestrator/` `ledger/` `report/` `heal/` | ~2900 | 基本通用（消息、队列、重试、台账、报表、自愈） |
| **引擎** | `page/` `verifier/` `core/`(部分) `sources/` `llm/` `ocr/` | ~3400 | 机制是通用的，但混入了业务词汇（见下） |
| **业务** | `batch/` `executor/` `gui/` `tools/` `config/`(部分) | ~8600 | 学平险的导入/校验/字典/状态机/复核 + 目标页面配置 |

其中 `core/` 要按文件分而不是按包分：`product.py` / `property_pool.py` / `property_source.py` 是引擎件，
`rule_engine.py` 的"按年级推荐保险方案档位"、`mock_data.py` 的投保 mock 是业务件。

### 2.2 依赖方向（现状）

```
  business(batch, executor) ──→ engine(page, verifier, core, sources)     ✅ 方向正确
  business(executor) ─────────→ business(batch.validator)                 ⚠️ 业务借业务的规则
  engine / infra 内部含业务词与业务规则                                    ❌ 边界漏
  page/dropdown 与 batch/dictionaries 两份"归一化"实现，靠注释声明一致      ❌ 重复实现
  engine ──→ business 的真 import                                          ✅ 不存在（底线还在）
```

### 2.3 泄漏清单（10 处，可直接核对）

| # | 位置 | 漏了什么 |
|---|---|---|
| 1 | `page/matcher.py:18-25` | `_keyword_map` 硬编码「学生姓名/监护人姓名/保险方案/保险员姓名」——引擎的匹配器认识保险字段 |
| 2 | `page/scanner.py:158` | 示例 locator 直接用「监护人电话」 |
| 3 | `core/rule_engine.py:85-100` | `recommend_by_grade()` = 按年级推荐**保险方案档位**，是业务规则 |
| 4 | `core/mock_data.py:52-53` | 投保 mock 数据 |
| 5 | `orchestrator/queue.py:61`、`orchestrator/worker.py:38`、`ledger/db.py:33` | 基建与台账里用 `applicant`（被保人）当列名 |
| 6 | `report/alert.py:51` | 报警文案写死"检查投保页是否改版" |
| 7 | `batch/runner.py:233-360` | 业务模块里内联浏览器动作（`_run_playwright` / `_fill_record` / `_fill_once` / `_submit` / `_screenshot`） |

## 三、目标结构

```
engine/                        # 不懂业务、不懂消息、不懂台账
  locate/    scanner / matcher / llm 定位降级
  act/       filler / dropdown / date_picker / overlay 把关
  verify/    checker（回读校验）
  recipe.py  Recipe / FieldSpec 模型 + 加载器
  probe.py   探针（字段清单由 Recipe 提供，机制在引擎里）
  sources/   excel / 证件 OCR / 户口本 OCR / 全局信息（可插拔数据源）
  runner.py  FillEngine：open → fill → verify →（可选）submit   ← 新增，唯一入口

infra/                         # 不懂业务、不懂页面
  gateway/  orchestrator/  ledger/  report/  heal/

business/
  insurance/    batch/（导入/校验/字典/期限/复核/状态机）
                feishu_adapter.py（原 executor/run.py）
                config/（recipes/学平险.yaml、import_mapping.yaml、options_*、*_aliases.yaml）
  safety/       （未来：多维表格 + 审批为主，少量外部系统录入时调引擎）
  training/     （未来：入口收敛 + OCR/解析 + 多维表格）

gui/  tools/                   # 消费者：可以 import 任意层
```

**边界规则（用测试固定，不靠约定）**：

1. `engine/` 不得 import `infra/` `business/`；源码里不得出现业务词黑名单
   （`投保/被保险人/监护人/年级/学校/方案/保费` …）。
2. `infra/` 不得 import `engine/` `business/`。
3. `business/*` 之间不得互相 import（共享的东西下沉到 engine 或 infra；
   例如期限规则属于保险业务，`resolve_period_floor` 应留在 `business/insurance/`）。
4. 只有 `gui/` `tools/` `tests/` 可以跨层随意引用。

> 为什么不分仓库：三条业务共享同一套 infra 与引擎、共享测试基建；
> 现在拆仓库会把"复用"变成包管理成本。**一个仓库、三层目录**是当前量级的最优解。

## 四、引擎契约（草案）

```python
# engine/recipe.py —— 一份"这个页面怎么填"的完整说明（数据，不是代码）
@dataclass
class FieldSpec:
    key: str                      # 业务字段名（如 school）——引擎不解释它的含义
    label: str                    # 页面上的可见标签（探针用）
    kind: str                     # text | choice | click | date | verify_only
    locator: str = ""             # 明确 locator（品种配置给的）
    label_keywords: tuple = ()    # 自动定位关键词（原 matcher._keyword_map 的内容，改为数据）
    options_file: str = ""        # 权威选项集（探针产物）
    aliases_file: str = ""        # 别名表（探针产物）
    depends_on: str = ""          # 级联上级（学生类别 → 年级/班级）
    required: bool = True

@dataclass
class Recipe:
    name: str
    open: OpenSpec                # URL / 二维码 / 入口方式
    fields: list[FieldSpec]
    validators: list[str]         # 业务校验规则名，实现在 business 里注册
    verify_keys: list[str]        # 回读校验哪些字段
    submit: SubmitSpec            # 默认 False；是否需要人工卡点

# engine/runner.py —— 唯一执行入口
class FillEngine:
    def run(self, recipe: Recipe, values: dict, *,
            submit: bool = False, on_event: Callable | None = None) -> FillResult: ...

@dataclass
class FillResult:
    filled: dict                  # 实际写入的值
    diffs: list                   # 回读差异（空 = 完全一致）
    screenshots: list
    errors: list
    submitted: bool
```

**与现有代码的对应关系**：

| 新契约 | 来自现在的 |
|---|---|
| `Recipe` | `core/product.py` 的 `Product` + `config/recipes/*.yaml` + `options_*.yaml` + `*_aliases.yaml`（合成一份"场景"） |
| `FieldSpec.keywords/options/aliases` | `page/matcher.py._keyword_map`、`batch/probe.py.PROBE_FIELDS`、各 options/aliases 文件 |
| `FillEngine.run` | `batch/runner.py` 的 `_run_playwright/_fill_record/_fill_once/_submit` + `page/filler.py` |
| `FillResult` | `batch/runner.py.RecordResult` + `verifier/checker.py` 的 diffs |
| `validators` | `batch/validator.py` 的规则（业务实现，引擎只按名调用） |

- 守卫跑出的真实泄漏清单（P2 的清理清单，按文件）：
  `core/mock_data.py`（学校/年级/班级/监护人）、`core/rule_engine.py`（年级/班级）、

## 六、不做什么

1. **不做"AI 看页面自己猜字段"的完全通用填表** —— 本项目的实测结论就是"猜不可靠"：
   探针采权威选项 + 显式配方 + 回读校验才是可靠路径。引擎的通用化靠**配置**，不靠模型。
2. **不引入插件框架 / DI 容器 / 事件总线** —— 三条业务的量级不值得，契约 + 目录 + 守卫测试就够。
3. **不为了"分层好看"改业务行为** —— 每一步都要有测试兜底，行为不变只是位置变。
4. **不一上来就物理搬目录** —— 先契约和守卫，再按收益搬（P1 只搬编排，P2/P3 才搬文件）。

## 七、这条拆分在面试里怎么讲

> "一开始只有学平险一个场景，页面知识、业务规则、浏览器动作都混在一起。
> 接第二条业务时我做了一次拆分：把'**怎么操作页面**'抽成引擎——定位协议、遮挡处理、
> 下拉面板作用域、日期闭环修正、回读校验；把'**这个页面长什么样**'压进配方配置；
> 把'**这条业务要什么**'留在业务层。然后写了一个架构守卫测试，用 AST 扫 import 边和业务词黑名单，
> 防止边界重新长回去。
>
> 判据很简单：**引擎代码里不许出现任何业务名词**——出现了就说明没抽干净。
> 拆完之后'新增一条业务'的代价从'改引擎'变成'加一份配置 + 一个校验规则集'。"

## 八、外部对照：MaaFramework 做过同一个动作

MAA（2021-07 首发，明日方舟单游戏脚本，.NET）→ **MaaFramework**（2023-04 独立建库，C++20，LGPL-3.0，
官方定位"基于图像识别的自动化黑盒测试框架"）。官方说法是用 MAA 的经验"去芜存菁、完全重写"。
**这和本设计要做的是同一个动作**：把一个单场景脚本里"怎么操作目标"抽成框架，
把"这个目标是什么"变成资源包。它验证了这条路的可行性，也给出了几个可以直接抄的做法。

| 维度 | MaaFramework | FormPilot（目标结构） |
|---|---|---|
| 引擎（怎么操作目标） | 框架本体：截图 + 输入的黑盒控制（Android 模拟器/真机、Win32 桌面、macOS/Linux） | `FillEngine`：Playwright + DOM 定位 + 遮挡/下拉/日期闭环 + 回读校验 |
| 场景描述（这个目标怎么操作） | **Pipeline JSON**：节点 = recognition + action + `next`/`on_error`，**图结构**（`[JumpBack]` 回跳、anchor、timeout、rate_limit；多文件递归加载） | `Recipe`：字段/类型/locator/选项集/级联/校验/回读/提交策略（目前是**列表**，不是图） |
| 业务包（一条业务） | **Bundle 资源包** = pipeline JSON + 图片模板 + ONNX 模型 + `interface.json`；Resource 可多 Bundle **按序叠加覆盖** | `business/insurance/`（配方 + 校验规则 + 字典 + 状态机 + 配置） |
| 扩展点（配置做不到的） | 自定义识别 / 自定义动作，**必须写代码**并经绑定注册；Agent 模式可拆到独立进程 | `validators` / `sources` 插件（业务实现，引擎按名调用） |
| 语言绑定 | C++/Python/NodeJS/C#/Go/Rust（官方各自独立仓库） | Python 单语言（当前量级够） |
| 低代码工具链 | 官方口径"**低代码**"：MaaPipelineEditor（拖拽建图）、VSCode 插件、MaaDebugger、MaaInspector | `tools/probe_options.py`（探权威选项）——是这个生态的雏形 |
| 分发 | GitHub Release + 镜像 + **MaaHub 社区中枢**（共享流水线/自定义模块/教程） | 自用，暂无 |

**四个可抄的点**：

1. **资源包可叠加覆盖**（基础包 → 细分包 → 局部差异包）。保险品种天然是"基础 + 机构差异"，
   比我们现在的"每个品种一份完整 yaml"更省维护。
2. **图式流水线**：`next` / `on_error` / 回跳 / 锚点 / 超时 / 限速。我们的 Recipe 只有字段列表，
   遇到"下一步取决于上一步结果"（分支、回跳重试）就不够用 —— 值得升级成 steps 图（轻量版）。
3. **"自定义逻辑必须出代码并注册"**——我们"引擎不许出现业务词、业务规则注册进来"的判据，
   在一个成熟框架里是同一种划法，说明这条边界是对的。
4. **配套工具链决定可用性**：编辑器 + 调试器 + 识别结果查看器。我们的探针相当于 MaaInspector，
   调试器和可视化编辑器是后续可以补的（P4 之后）。

**一个关键区别（也是我们的立身之地）**：MaaFramework **没有 DOM/HTTP 能力**，只能截图 + 坐标点击，
官方没有任何网页/表单自动化的场景声明。它能操作任何"可截图的目标"，但**读不回来、校验不了选项集**。
我们做的是网页表单的结构化填写（DOM 定位 + 权威选项集 + 回读校验）——**互补，不竞争**：
它够得着的场景更宽，我们够得着的场景更准；而"准"在保单/报名这类场景是硬要求。

## 九、替代方案盘点：为什么还值得自己做

| 类别 | 代表 | 结论 |
|---|---|---|
| 商用 RPA | UiPath、Power Automate Desktop、**影刀**、UiBot/来也、金智维、艺赛旗 | 能做，但面向"流程编排"而非"单据级正确性"；重、贵、项目制交付。金智维/艺赛旗的保险录单就是项目制领域 |
| 浏览器开源工具 | Automa（21.7k★，块式，无 AI）、UI.Vision（录制回放 + CV/OCR）、Selenium IDE（停更）、Playwright codegen（定位器生成器，非填表产品）、TagUI（原厂停维护） | 都停在"动作层"，没有"填完必回读 + 选项集校验" |
| **AI / GUI Agent** | browser-use（117.8k★，最热，登录态/CAPTCHA 受限）、**Skyvern**（23.2k★，最接近：视觉 LLM + Playwright 专攻填表/登录，但**自报 WebBench 准确率仅 64.4%**）、Stagehand（MIT，SDK）、Claude Computer Use（慢/贵/prompt injection）、OpenAI Operator（已并入 ChatGPT agent）、UI-TARS（Beta）、Mobile-Agent、**Playwright MCP**（微软官方，用 a11y 树而非截图，稳定省 token，但只提供动作、无业务校验） | **没有"视觉 LLM 直接操作网页"的开源项目被广泛用于生产**；生产里赢的是"结构化 DOM/a11y + 确定性流程"，视觉只做兜底 |
| 行业方案 | 金智维/艺赛旗/弘玑/来也/达观/合合 + 云厂商文档智能 | 路线是 OCR → 字段映射 → RPA/接口补录 → 规则校验；**没有"任意投保页即插即用"的标准化成品** |

**两个真空白**：

1. **"Excel → 网页表单批量填写"的开源项目基本是空白**（表单类头部项目都是 PDF 表单库；网页填表项目 <50★）。
2. 现有方案普遍缺：**权威选项集校验、填后回读校验、中文政企 H5 的怪页面适配（iframe/级联/自定义组件/日历控件）、
   人工卡点、审计留痕**。前四项是我们已经在做的，第五项（`task_step` 留痕 + 截图 + 台账）比 Skyvern 那类更完整。

**面试答法**：> "RPA 不校验、Agent 不准且不可控，而保险场景错一格就是合规事故 ——
> 所以我把模型当兜底而不是主路径：定位用探针采的权威配置，填写走确定性流程，填完必须回读。"

---

**"项目制交付" vs "配置驱动"的区别**（同一件事的两种卖法）：

| 维度 | 项目制（厂商驻场/远程实施） | 配置驱动（引擎 + 配置） |
|---|---|---|
| 交付物 | "**这个**客户的**这个**系统能跑" | 引擎 + 一份页面配置（可继续加） |
| 适配新页面 | 新一轮实施（人天～人月，要重新报价） | 加配置（小时级） |
| 页面改版 | 报障 → 重新实施 | 重跑探针 → 改配置 |
| 谁来做 | 厂商实施工程师 | 业务方自己（或我们） |
| 成本结构 | 卖人力，**线性** | 引擎一次投入，配置边际成本趋零 |

诚实边界：项目制能覆盖我们覆盖不了的（必须人工判断的弹窗、验证码、无稳定结构的页面）；
配置驱动的前提是"**页面是稳定的表单结构 + 权威选项可采**"。
一句话：项目制是把"不可复用"当商品卖，我们是把"可复用"沉淀成引擎、把"不可复用"压成配置。

**成本模型（token 到底花在哪）**：

| 环节 | 成本 |
|---|---|
| 探针采权威选项 + LLM 辅助定位 | **一次性**（每页面/每次改版一次）；固化进 `product_library/*.yaml` 的 `field_mapping` 后不再调用 |
| Excel → 网页填写（N 条） | **0**（字典归一化 + Playwright 填值 + 回读校验，纯确定性代码） |
| 证件照 OCR | 按次计费（腾讯云 0.15 元/次；本地 PaddleOCR 兜底 0 元）——**不是 token** |
| 飞书收发消息（含机器人主动推送） | **0**（纯 API 调用；消息路由是关键词规则匹配，不是 LLM） |
| 需要"理解"的消息（自然语言报名、聊天截图抽信息） | 这一步才消耗 token |

> 结论：**消息本身不消耗，消息的"理解"才消耗；定位是一次性的，填写是零成本的。**
> 用 119 条学平险举例 = 1 次定位 + 118 次零 token 执行。

## 十、三个常被问到的质疑（含答法）

**① "整理数据源不也要时间？我边整理边填不就完了"**

- 关键不是第一次，是**第 N 次**：只做一次、且数据源要额外整理出来的，自动化不划算 —— 这种明确不做。
- 学平险的数据源不是为自动化额外造的，是**业务过程自带的产物**（学校的收费名单 / 保险公司的台账），本来就存在。
- 手工路径同样要"整理"（对着原始数据逐项核对），只是把核对混进了填写动作里、看起来没成本；而出错要返工。
  自动化把这一段变成**校验**（身份证校验位 / 手机号 / 查重 / 字典匹配）——这才是顺带的真价值。
- 实测：119 条里学校有 **19 种写法**、年级有 **18 种写法**；"在网页下拉里找到这该算哪个选项"正是手工 3-5 分钟/条的主要成分。

**② 弹窗 / 验证码 / "无稳定结构"到底指什么**

| 情况 | 能不能覆盖 | 处理方式 |
|---|---|---|
| 有唯一答案的弹窗（关闭 / 确定） | ✅ | 遮挡把关，**每次点击前**过一遍（学平险的须知弹窗每次点击都重现——实测结论） |
| 需要业务判断的弹窗（"信息有变更，是否继续？"） | ❌ | 停下来问人（人工卡点） |
| 不可关闭的强拦截（登录失效、短信验证、风控"稍后再试"） | ❌ | 转人工 / 等待；**明确不做破解** |
| 验证码 | 正常启动的页面**没有** | 前提是"做用户本来要做的事 + 低频 + 已登录会话"；同账号高频连击可能触发风控 → 靠**限速 + 串行 + 提交默认关闭** |
| "无稳定结构" | 不是"页面实时在变" | 三种：① DOM 随状态/数据变（动态渲染、随机后缀 id）② **只是代码在变、页面没变**（改版）③ 真无 DOM（canvas / 纯图片表单）→ 走图像识别路线或不做 |

三层保险：显式 locator（探针采权威配置）→ **回读校验**（发现没填上/填错）→ 异常自愈（小改动靠错误的"形状"命中历史案例）。

**③ "视频里飞书能……豆包能……，这些算不算被覆盖"**

| 视频里看到的 | 本质 | 与我们的关系 |
|---|---|---|
| 飞书多维表格 / 审批 / 机器人 | 平台原生低代码 | **直接吃**——是地基，不重复造 |
| "AI 助手答问 / 写日报" | 平台能力 + LLM 对话 | 我们做的是它的"业务版"：真实数据 + 异常处理 + 留痕 |
| 豆包一类 | 对话与生成；**不会替你点网页、建队列、校验身份证** | 流水线里的一个**可选环节** |
| "AI 自动操作电脑/手机" | GUI Agent | 同目标、不同路线：我们赌确定性，它赌泛化 |
| 视频不讲的：幂等、重试、权限、审计、校验、人工卡点 | 工程化 | **这正是我们的内容**——演示能跑通一次，我们要跑 119 次不出错 |

判据：**平台能做的别做（配置），平台做不了的才是代码**（批量、校验、幂等、跨系统、留痕）。

## 十一、能力延伸：换目标 = 换 driver，不是重写引擎

**边界不在"网页 vs 桌面"，而在"目标提供了多好的锚点"**。优先级从高到低：

```
接口 / 文件导入  >  网页 DOM  >  桌面控件树(UIA)  >  图像识别  >  纯坐标点击
（最稳，优先）                                        （最脆，兜底）
```

很多"ERP 客户端"其实是**套壳网页**（Electron / CEF / WebView2），本质还是 Chromium、还有 DOM：
判断方法是看安装目录有没有 `resources/app.asar`，或者尝试连它的 CDP 调试端口 ——
能连上就用 `connect_over_cdp` 复用现有引擎，**零架构改动**。
确认是原生控件程序（Win32/WPF/Delphi/Qt）则换用 **UI Automation**（pywinauto / FlaUI / WinAppDriver）——
它相当于"桌面版的 DOM"，按 automation id / name 定位，和坐标点击不是一个可靠性量级。
只有**控件树也不可用**（自绘 UI、老 Swing 系统、远程桌面里的程序）时才轮到图像识别。

`Locate / Act / Readback` 三个能力抽成 driver 接口后，换目标只是加一个 driver：

| driver | 定位方式 | 回读方式 | 可靠性 |
|---|---|---|---|
| `web`（现有） | CSS / placeholder / aria-label + 探针配置 | 元素 value / innerText | 高 |
| `desktop`（待做） | UIA automation id / name path | 控件 Value 属性 | 高（需目标可访问） |
| `image`（兜底） | 模板匹配 / OCR / 颜色 | **只能再截一次图比对** | 低 |

**要借 MaaFramework 吗？** 它是"黑盒控制"框架（截图 + 模拟输入），对应上表的 `image` 行——
只有在"没有接口、没有控件树、也没有稳定图像特征"的目标上才有意义，而且它**没有回读语义**
（读完只能再截图），我们仍需要自己的校验层。所以现阶段不是"引入它"，而是"照它的思路留一个 image driver 的位置"。

## 十二、浏览器与中断加固

**浏览器现在怎么开的**：Playwright 自带的 **真实 Chromium**（同内核，不是"模拟浏览器"），
每品种用 `context` 段声明环境（`mobile` / `wechat` / `referer`——太保页必须用移动 UA 才渲染）。
它与你日常 Chrome 的差别只在于**用户数据目录不同**（干净 profile，没有你的登录态与扩展）。
两种"用我自己那个浏览器"的正规做法：

- `launch_persistent_context(user_data_dir=...)`：登录一次、cookie 留存（项目里 `llm/web_client.py`
  给 DeepSeek 网页版扫码登录用的就是它）
- `connect_over_cdp("http://127.0.0.1:9222")`：连到你自己已登录的 Chrome（需以
  `--remote-debugging-port=9222` 启动）——飞书那条链路当时就是用这一招

> **已定**：目标系统需要登录 → 走 `connect_over_cdp` 连**系统 Chrome 的专用 profile**
> （`--remote-debugging-port=9222` + 独立 `--user-data-dir`）：真实浏览器 + 亲手登录过的会话，
> 又不与日常浏览抢标签页。注意：新版 Chrome 出于安全会拒绝在**默认数据目录**上开调试端口，
> 所以必须用独立目录（动手时实测一次确认当前版本行为）。
> 这样也顺带解决了"profile 被占用"——专用 Chrome 是唯一入口，程序只是连上去。

**中断加固清单**（不追求"不中断"，追求"**知道停在哪、能安全续跑、绝不重复提交**"）：

| 中断来源 | 现状 | 要补 |
|---|---|---|
| 弹窗 / 遮罩 | ✅ 遮挡把关（每次点击前过） | — |
| 原生 alert / confirm | ⚠️ 未注册 dialog handler 时 Playwright 自动关闭 —— 不会挂死，但"确认提交?"可能被当"取消" | 按情况显式 accept/dismiss；判不了的记事件转人工；靠回读校验兜住 |
| 页面改版 / 没填上 | ✅ 回读校验 + 异常自愈 | 探针重跑流程 |
| **进程被杀** | ✅ "录入中 → 已确认"重置，重启续跑（`batch/runner.py` 头注释即此设计） | 浏览器残留进程清理 |
| **重复提交** | ✅ 提交默认关闭 + 人工卡点——中断后重跑不会重复投保（**最重要的一道防线**） | — |
| 浏览器 / profile 被占用 | ❌ 表单路径还没用持久化 profile，也还没有锁 | 要用 persistent profile 就得配 profile 级单实例锁（照抄 `feishu_bot.lock` 那套：PID + 失效接管） |
| 登录失效 | ⚠️ 会失败并留痕 | 检测 + 明确提示 + 持久化会话 |
| 主机休眠 / 锁屏 / 断网 | ❌ 无看门狗 | 批量前检查电源策略；失败重试；长任务分片 |
| 无限重试 / 卡死 | ✅ 有界重试 + 退避 + 卡死恢复 | 全局看门狗 |

---

**会话生命周期（把 profile / 登录失效 / 续跑串起来看）**：

```
一次登录 → 持久化保存（persistent profile 或 CDP 借用户浏览器）
        → 运行中检测失效（出现登录框/跳登录页）
        → 人工重登 → 从状态机记录的断点续跑
```

- **"干净 profile 每次都重新登录"与"持久化 profile"不是两个功能，是同一机制的两种状态**：
  Playwright 默认的 `new_context()` 不落盘（无登录态、关掉即消失、可并发）；
  `launch_persistent_context(user_data_dir=...)` 落盘（登录一次留下 cookie，但**同一目录不能被两个进程同时用** → 需要 profile 级锁）。
  第三条路是 `connect_over_cdp`：借用户自己已登录的浏览器，登录态最"真"，代价是浏览器得手工开着。
- **登录失效 ≠ profile 问题**：持久化只减少"登录次数"，不防"会话中途过期"。失效要**运行时检测**（识别登录页/登录框）→ 停下来提示人工重登 → 靠状态机的断点续跑，不重头再来。

**加固优先级**：既然每条数据都有人工复核，中断的代价被人工兜住了一大半，所以
看门狗、电源策略、profile 锁这些可以排在 P1 之后。但**两条不能后置**：
① **重复提交防线**（提交默认关闭 + 幂等），② **断点状态标记**（"录入中 → 已确认"重置，否则重跑会重复填）。
另外要选清复核粒度：**逐条复核**（人盯着，中断代价小、吞吐低）还是**批量复核**（填 N 条一起看报告，
吞吐高、但中断后要靠状态标记判断哪些填过）。

## 十三、输入源：把可插拔数据源变成一等配置

**现状**：架构其实已经可插拔 —— `PropertySource`（抽象基类：`get_fields` / `extract` / `is_input_ready`）
+ `sources/factory.py` + `PropertyPool` 合并。已有四个源：身份证 OCR、户口本 OCR、Excel 名单、保险员信息。
**但**：`_SOURCE_CLASSES` 是一张**硬编码字典**，源的启用靠 **GUI 属性面板手工拖图**，
配方/配置里没有声明 —— 这就是"只做 Excel 太基础、OCR 像是私人定制"的来源：**能力在，接线没配置化**。

**目标**：在 Recipe 里声明输入源与优先级，让"加一个源"= 写一个类 + 一行注册。

```yaml
inputs:
  - source: excel                       # 列映射
    map: {学生姓名: name, 身份证号: id_card, 手机号: phone}
  - source: idcard_ocr                  # 只在缺字段时补
    provide: [name, id_card, gender, birthdate]
  - source: nl_text                     # 一句话 / 消息文本
    pattern: "报名 {name} {project} {company} {phone}"
  - source: manual                      # 人工补录
resolve:
  order: [manual, idcard_ocr, nl_text, excel]   # 优先级：前者覆盖后者
  on_conflict: report                   # 两源不一致**不自动选**，报异常给人
```

三条规则：① 新增来源 = 一个类 + 一行注册（不动引擎、不动 GUI）；② **字段级**来源与优先级写在配方里
（可版本化、可 review）；③ 多源冲突不猜 —— 与"字典不猜、缺字段不猜"一脉相承。

**分层澄清（"属性/字段到底属于谁"）**：

| 层 | 内容 | 换业务要不要改 |
|---|---|---|
| 引擎 | `PropertySource` 抽象接口（`get_fields` / `extract` / `is_input_ready`） | 不改 |
| **业务词汇** | 字段名清单（学生姓名 / 身份证号 / 监护人电话 …）——**领域知识，不存在通用答案** | 要配（这是应该的） |
| **数据适配** | 列名字典：同一字段的各种写法 | 要配，但**可积累** |

**列名字典已经做出来了**（`config/import_mapping.yaml` + `batch/importer.py:ColumnMapper`）——
你说的"同一列在不同表里叫 身份证 / 身份证号码"正是它解决的问题，而且比"一张字典"更细：

- 三级匹配：**精确 → 归一化（去空白 / 全角转半角）→ 包含匹配**；命中多个按别名先后顺序取第一个
- `ignore_columns`（序号/申请状态/备注 等不导入的列）
- `ignore_placeholder_values`：把"（此处填写）""N/A"这类**占位符当空**（OCR 会把提示文字识别进来）

**要补的是两条**：① 这张字典目前只服务 Excel 源，应升级为**源无关的字段字典**（OCR / 消息解析 / 人工录入
都走同一套字段名，不再各写一份）；② "认不出来的表头"要有**反馈通道** —— 记成待确认项、确认后并入字典
（与 Video2Team 的 `corrections_pending` → 确认 → 本地生效 是同一个模式），让字典能积累而不是每次人工找。

**OCR 的定位**：它是**内置源（能力）**，默认可用；配方里的 `inputs` 是**可选声明**——
声明了才"自动跑"，不声明也能在 GUI 里手工拖图。所以：**能力在引擎（不进配置），启用方式在配方（可选配置）。**

### 13.1 接入向导：页面 + 脱敏样例 → 属性、字典、规则

现有向导（`gui/product_wizard.py`）已经五步：命名 → 从属性库选属性 → 输 URL（支持二维码导入）→
扫描页面字段（只读展示）→ 确认/修正映射 → 存品种。缺的正是"**把你平时填表用的那份表格也喂给向导**"。
加进去之后，一次接入同时产出四样东西：

| 产出 | 从哪里来 | 落到哪 |
|---|---|---|
| 属性清单（业务词汇） | 样表表头 + 页面字段标签，两边对齐 | 属性库 |
| **列名字典条目** | 表头 → 标准字段（"身份证号码"并入 `id_card` 的别名列表） | `import_mapping.yaml`（**字典自动积累**，补上上一节说的反馈通道） |
| 字段类型与校验规则 | **从样例值格式推断**：18 位含 X → 身份证；11 位 `1[3-9]…` → 手机；"8.22-8.21" → 期间文本 | Recipe 的 validators |
| 页面字段 ↔ 数据列 初始映射 | 字段名/标签匹配 + LLM 建议（可选、可关） | Recipe 的 `field_mapping`（**人工确认后**才固化） |

**三条硬要求**：

1. **脱敏要保格式**：疑似敏感列（身份证/手机/银行卡）替换成**同格式假值**（位数、字符类型一致）——
   否则推断不出校验规则（把身份证换成 `***` 就等于把规则信息也删了）。
2. **真实值不进 LLM**：语义匹配只用"列名 + 页面字段标签"（必要时用掩码后的样例），真实值不外发。
3. **建议必须人工确认**（不猜原则）；认不出的表头进**待确认队列**（与 Video2Team 的
   `corrections_pending` → 确认 → 本地生效同一模式）。

**副产品**：脱敏样例 + 页面快照 = 一份**可回归的测试夹具**（沿用 `tests/test_mock_full_page.py` 的套路）——
新业务接入自带测试，而不是接入完再补。

**实施顺序**：先做离线部分（读脱敏样例 → 生成属性/字典/规则建议：纯逻辑、不依赖浏览器、好测），
再接进向导第 2 步（把"从属性库挑"升级成"从你自己的表里长出来 + 可手工补"）。

> 对照 MaaFramework：它的"支持一个新 APP"要人**手写 pipeline JSON**；
> 这条向导把同一步做成**半自动起草 + 人工确认**——这是能讲的差异点。

### 13.2 数据源是"零碎消息"时：聚合 → 抽取 → 主数据对齐 → 确认

场景：客户发"我要买今年的学平险" + 两张截图；换个业务就是"给华东定了 XX 两套"——
**公司和物品说的都是简称**，而主数据里存的是全称加编码。四步，每步的现状：

| 步骤 | 做什么 | 现状 |
|---|---|---|
| ① 聚合 | "文本 + 图片"两条消息合成一件事 | ✅ `gateway/aggregator.py`（hold 窗口 + msg_id 幂等） |
| ② 抽取 | 文本抽槽位（公司/物品/数量/时间）+ 图片 OCR | ⚠️ OCR 与关键词路由已有；**槽位解析要补**（规则 + 词表优先，LLM 兜底） |
| ③ **主数据对齐** | "华东" → 主数据里的"华东分公司（CODE-001）" | ⚠️ 有先例（`school_aliases.yaml` 等别名表）；公司/物品的别名表要建 |
| ④ 确认 | 回显让人确认；未识别的进待确认队列 | ❌ 要补 |

**③ 是真正的难点：实体对齐（简称 → 主数据），分级匹配**——和列名字典同一套思路，只是主体是"实体"：

| 级别 | 例子 | 处理 |
|---|---|---|
| 精确 | 全称 / 编码一致 | 自动填 |
| 归一化 | 去空白 / 全半角 / 去"有限公司"后缀 | 自动填 |
| 包含 / 前缀 | "华东分公司" ⊃ "华东" | **唯一命中**才自动；多个 → 给候选 |
| 模糊（编辑距离 / 拼音） | "华冬" → "华东" | 只给建议，不自动选 |
| 语义（LLM，可选） | "那家做汽配的" | 只给候选 |

**铁律：唯一命中才自动；多个命中或零命中，一律问人**（零命中 → 待确认队列 + 可现场新建）。

**④ 靠机器人完成"问人"**：

- **回显确认**（默认，够用）：回推"我理解为：华东分公司 / XX 产品 / 2 套 / 今天，对吗？回 1 确认，回 2 修改"
- **交互卡片追问**（更顺，要写事件处理）：把候选做成按钮让人点选
- **待确认队列**（异步版）：未识别实体累积后定期推给管理员批量确认，确认即并入别名表
  （同 `corrections_pending` 模式——确认一次，永久复用）
- **三个坑**：① 自定义机器人的卡片按钮**不支持服务端回调** → 必须用应用机器人（本项目已经是）；
  ② 追问要**限次**（两次不通就转人工，别无限追问）；③ 卡片回调要**幂等**（防重复点击建两条记录）

> 一句话：这条路的技术难点不在"读懂消息"，而在 **"知道自己在哪儿不确定，并且问得动"**。
> 把"猜"换成"问"，成本就从"猜错"变成"用户点一下"。

### 13.3 分工：平台 / 机器人 / 引擎，各是哪一段

问"能不能不用引擎做"，答案取决于走到哪一步：

| 环节 | 谁做 | 不写程序行不行 |
|---|---|---|
| 收消息 / 聚合 / 收附件 | **机器人**（gateway 接入层） | ❌ 平台做不到——要读私聊消息内容并自定义处理，必须应用机器人 + 自建服务 |
| 文本/图片 → 字段 | **引擎**（输入源层） | ⚠️ 多维表格的 AI 字段/自动化 AI 动作能做很轻的版本（能力边界未核实，别押注） |
| 简称 → 主数据 | **引擎**（别名表 + 分级匹配） | ❌ 平台做不到（把别名塞进选项集只能覆盖静态、无歧义的场景） |
| 回显确认 / 追问 | **机器人** | ❌ 必须程序（要事件回调 + 幂等） |
| 落库 | **平台**（多维表格），程序只调用 | ✅ 这就是平台原生能力 |
| 校验（校验位 / 查重 / 日期规则） | **引擎** | ❌ 公式最多做一点点 |
| 审批 / 权限 / 看板 | **平台** | ✅ 纯原生，别重复造 |
| 录进外部网页系统 | **引擎**（填表） | ❌ 平台完全没有这一层 |

**所以角色是**：机器人是**耳和嘴**（收发消息、问人），引擎是**手和眼**（读图、看页面、填写），
平台（多维表格 + 审批）是**账本和闸门**，业务规则与状态机是**脑**（orchestrator + validators）。
它们不互相替代，是分工：机器人调引擎干活，结果落进平台的账本里。

判断规则还是那一句：**平台能做的别做（配置），平台做不了的才是代码。**

## 十四、复核可视化：字段批注层 + 对比报告

**现状（你感觉"没怎么实现"是准确的）**：`verifier/checker.py` 已经输出结构化差异
`{property, expected, actual, locator}` —— **连 locator 都在里面**；但呈现只有
`gui/page_panel.py:131` 的一行文本（"· 学校名称: 期望「X」实际「Y」"），批量路径更是只有截图 + 文本报告。
**逻辑在，呈现几乎没有。**

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 页面内批注层**（推荐） | 差异项自带 locator → `bounding_box()` 拿坐标 → 注入独立浮层 `#fp-annotations`（`pointer-events:none`、高 z-index），在每个字段旁贴"期望值"（浅灰小字），不一致的描红框 | 视线零距离；**绝对定位浮层，不动原表单 DOM**（不污染页面、不被目标页校验读到） |
| **B. 归档对比报告** | HTML：期望 / 实际 / 状态三列 + 失败字段的裁片截图（`page.screenshot(clip=...)`） | 可留档、可发给别人、可当审计凭证 |
| C. 往页面贴原始表格截图 | Snipaste 式贴图 | ❌ 不贴 Excel 截图（冗余、可能含敏感列、未必对应当前记录）；要贴就贴**该条记录的小卡片**或**证件照缩略图**（核对身份证最有用） |

**批注层的交互**（Snipaste 手感）：快捷键（如 `Ctrl+Shift+A`）或角落按钮切换显示；双击浮层隐藏。

**✅ 已实现**（`engine/annotate.py` + `engine/report_html.py` + `tests/test_annotate.py`）：
方案 A 与 B 都已落地 —— 单条录入填完即贴批注（`page/filler._hold_browser`），
逐条确认时也贴（`BatchRunner._confirm_record`）；报告是单文件 HTML（期望/实际/状态 + 原始截图链接）。
C（贴原始表格截图）按上文判断不做。实现细节与差异：

- 位置用 `locator.bounding_box()` 算（locator 里可能有 `>> nth=` 这类 Playwright 语法，
  `document.querySelector` 处理不了）；浮层用 `position:fixed` + 滚动跟随
- 提交守卫按"**自动清理**"实现（`FillSession.submit_now` 先清再点，比报错更顺手）
- 已知限制：SPA 换视图后定位会失效 —— 批注只服务"人看"的复核时刻

**三条硬约束**：① 批注层**必须在提交/付款前清理**，并加守卫（存在 `#fp-annotations` 就不许提交）；
② 不得挡住自动化自己的点击（`pointer-events:none`，只有图片本体可交互）；③ **归档凭证用原始截图 + 报告**，
不用带批注的截图（批注是我们加的，别人看会混淆）。

**归属**：这是引擎能力不是业务能力（任何场景都要"填完看一眼对不对"）→ `engine/annotate.py` + `engine/report_html.py`，
业务只决定展示哪些字段。它也是"MaaInspector / 调试器"那一类的对应物。

### 14.1 校验与复核的三档策略（每个字段可配）

**✅ 已实现**：① 由 `verify_after_fill` 控制（品种向导第 5 步有勾选框，默认勾选）；
② 由新增的 `verify_tier`（`human` | `machine` | `spot`）控制人工呈现 —— 
批注层与报告都会跳过 `machine` 档的字段，**但出了问题的字段照样呈现**（降级不等于放过错误）。
③ 抽查（`spot`）目前只是 `human` 的同义档，降级提示与抽查统计留给后续。

| 档 | 谁在做 | 成本 | 建议 |
|---|---|---|---|
| **① 机器回读校验** | 程序读回页面值比对 | 毫秒级、零 token、纯本地 | **默认常开**（"用几次没问题就关"没必要关——它几乎免费，且是发现"没填上"的唯一防线） |
| **② 人工呈现（勾选框 / `verify_tier`）** | 人看差异/批注 | 占用人眼，这才是贵的 | 按字段类型给默认值：**OCR / 级联 / 日期 / 计算字段 → 默认呈现**；纯直填字段 → 可设 `machine`（减少视觉噪音） |
| **③ 降级为抽查（未实现）** | 连续 N 次一致 → 提示"该字段可降级" → 每 M 条全字段展示一次 | 低成本保留抽查 | **不静默关闭**；任何一次不一致、或字段被改过 → 自动恢复全量 |

### 14.2 批量 vs 逐条：其实是两个维度

| 维度 | 选项 |
|---|---|
| **执行** | 一次会话连填 N 条（省登录与加载） vs 每条重开会话 |
| **卡点** | ① 逐条确认（每条填完停下）② 批末确认（填完整批一次看报告）③ 仅异常停（无人值守 + 异常转人工） |

"打开一次网页、填 N 条、用户逐个确认然后提交" = **批量执行 + 逐条确认**。
**✅ `confirm_policy` 已实现**（`execute.confirm_policy: batch | per_record`，默认 `batch`）：

- `per_record`：每填完一条 → 先在页面上贴批注 → 调 `on_confirm` 回调要一个结论
  （**GUI**：`_RunWorker` 发信号回主线程弹"通过/打回"对话框，工作线程等答复，10 分钟兜底按打回；
  **CLI**：`tools/run_batch.py` 交互问一句，`--yes` 表示全部按通过）；
  打回 → 「录入失败」+ 原因"人工复核打回"；回调异常一律按**打回**处理（宁可人工再看一次，也不放行）
- `exception_only`：**只在异常时停** —— 正常条不打扰人；失败条先问一次，
  人认了仍进「待复核」（谁放行谁负责，状态写「异常经人工确认后放行」），打回就按录入失败记
- 未实现：`spot` 抽查统计（连续 N 次一致才降级）

原来的行为（`batch`）保持不变：runner 串行逐条填 → 每条截图 → 状态置「待复核」→
整批跑完后人工复核（reviewer 有异常优先队列 + 通过/打回/批量通过），提交全人工。
**归档对比报告**（`engine/report_html.py`）每批自动生成一份，路径在 `RunReport.html_report`
（GUI 弹窗里给出、CLI 打印出来；`execute.report_html: false` 可关）。
建议把这三种做成配置 `confirm_policy: per_record | batch | exception_only`（默认 `batch`）。

> 取舍：**逐条确认会显著拉长会话时间**（N 条 × 人工时间），会话越长越容易掉登录或被风控；
> 所以大批量（≥50 条）用批末确认 + 异常优先，逐条确认留给小批量或高风险条目。

> **已定（本项目）**：`per_record`（逐条确认）。理由来自业务本身——**录入系统里填错了删不掉**
> （撤销要么走后台、要么留下脏数据），逐条确认换来的是"绝不产生错数据"，比吞吐优先。
> 两点补充：① **逐条确认 ≠ 逐条重开页面**——一次会话连续填 N 条，每条填完停下来让人核对，
> 确认后再继续（页面不重开、不重登录）；② 此时**报告退化为归档证据**（留痕用），
> 复核主界面是**页面内批注层**（填完当场看期望值，一眼扫过就确认）。

### 14.3 报告与台账分层（Excel 是对账的载体，不是证据的载体）

| 层 | 载体 | 内容 | 给谁 |
|---|---|---|---|
| **证据** | HTML 报告 + 原始截图 + `task_step` 留痕 | 期望/实际/状态三列、失败字段裁片、整页原图、时间戳与操作人 | 人看、归档、必要时当凭证 |
| **台账** | SQLite（`ledger` / `task_step`） | 条数、耗时、成功失败、提效分钟数 | 程序统计、日报 |
| **导出** | Excel / CSV（从台账导出） | 结构化数据、可加批注列 | 财务对账、业务方 |

**不要**拿 Excel 当审批/执行留痕（可被改、无时间戳、无操作人），也**不要**拿带批注的页面截图当凭证
（批注是我们加的，别人看会混淆）——证据靠"原始截图 + 结构化差异 + 不可变留痕"。
